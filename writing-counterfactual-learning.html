Can Counterfactual Learning Help Us Be More Efficient?

Note: This post is a work in progress — I'll be adding plots and more content soon. Also, if you have idle GPUs and found this blog interesting, I would very gratefully put them to work (these experiments are done on remaining Stanford Modal credits).

Can models learn more quickly by testing alternative ideas and figuring out which experiences are worth learning from?

When humans learn how to drive, for example, we can perhaps learn more quickly by thinking about what not to do as opposed to strictly what to do. Driving is inherently so multimodal and learning what not to do constrains the span of what to do. When I was learning how to drive in Texas (I got my license very sample-efficiently in ~2 weeks of practice of ~1 hour every other day or so), I recall once being at a red light and my instructor trying to get my attention:

The man, absolutely chugging his coffee at 7:30am in the morning, in his thick Texan accent exclaimed "c'mon kid, go right on red! It's clear"

As an intro driver, you could say I quite literally went right on red (i.e., I drove straight, interpreting "right on" as a Texan proxy for "just go straight kid"). As you can imagine, the instructor slammed the brakes and yoinked the steering wheel. But the important thing here is that I learned a lot by that mistake, so much so that I was extra cautious during the actual test (I still do not know how to parallel park). This makes me wonder if models can learn to actually be smarter by learning what not to do.

Some vocabulary

To begin, let's define some relevant vocabulary to be consistent in the blog. The learner in this blog is the main model we are currently training, the reference model is a smaller model that we train once on separate data (we use its loss to estimate which examples may be inherently difficult to learn). A "horizon" is how long we choose to train before comparing methods (e.g., 6,000 steps vs 1,000 steps or 3.14159 steps :D).

A batch is a small group of text used for one parameter update, a pool is the larger collection of text from which batches can be sampled, and a pass over the pool means processing approx. as many training tokens as the pool actually has.

We also relevantly focus on the idea of data-efficiency in this blog, where data-efficiency is evaluated on three main objectives:

  1. Same trained tokens (i.e., both methods perform parameter updates on the same number of tokens; i.e., which method learns more from the same amount of actual training data?)
  2. Tokens to target (i.e., we count how many update tokens one method needs to reach the other method's final validation quality; i.e., how quickly does each method reach a given quality level?)
  3. Same total work (i.e., selection must pay for examining candidates that it rejects; we thus give uniform training the same compute budget as additional training updates).

We use the official BabyLM 2026 Strict-Small text corpus and the same held-out evaluation data within each comparison.

Detached local training

To begin, we try to guide the actual activity inside the transformer by questioning the backprop process.

As a quick refresher, a transformer is a stack of blocks (e.g., block 1, block 2, etc. final prediction voilà). Each of these blocks produces an activation, a large table of internal numbers that becomes the next block's input (i.e., we feed in and help build a better representation through those layers).

Ordinary backprop starts with the final prediction error and sends the exact credit info backward through every block.

We begin by testing a cheaper alternative called detached local training. Before one block's output enters the next block, the implementation would call detach() and the activation would still travel forward normally, but the gradients can't cross that specific boundary.

I.e., block 1 → stop gradient → block 2 → stop gradient → block 3

In detached local training, we attach the language-model output head directly to every block (each block receives its own local next-token loss):

Block 1 output → vocabulary prediction → local loss 1 Block 2 output → vocabulary prediction → local loss 2 … Block 8 output → vocabulary prediction → local loss 8

For each block, we normalize its output, project it through the same vocabulary weights used by the model's output head, and calculate next-token cross-entropy (and average that error across tokens and examples). Those vocabulary weights were detached along the local loss path.

Thus, a local loss therefore asks: Could this block's current representation already predict the next token?

But this didn't tell the block how later blocks would transform that representation. So, the missing long range info that we thought about here was how does an early block's activation affect the true final loss after all later blocks process it?

In ordinary backprop, we calculate this with the chain rule; this detached approach removes it.

Counterfactual local credit

Here, we introduce the idea of counterfactual local credit, or CLC, which tries to recover some of the missing information using forward experiments.

Suppose \(H\) is the activation after block 4. We can choose a small direction \(u\) and run the remaining blocks twice:

H + εu → later blocks → loss+ H − εu → later blocks → loss−

where \(\varepsilon\) is a small step size. Thus, the directional slope is approx.

\[ \text{slope} = \frac{\text{loss}^{+} - \text{loss}^{-}}{2\varepsilon} \]

When this slope is positive, toward \(+u\) raises the loss (i.e., moving towards \(-u\) appears to be helpful). When it is negative, moving towards the \(+u\) appears to be helpful.

We repeated this experiment for several directions and for each direction \(u_i\), we measured a slope \(s_i\) and combined the results as a scaled average of \(s_i u_i\).

Thus, the result was an approximate activation gradient: a vector estimating how changing the block's output would then change the downstream loss.

Now, because these activations exist only for the current batch, directly changing an activation would not permanently teach the model. So, we create a local surrogate loss whose gradient matches the estimated activation credit (and backpropagating that surrogate through the current block changes the block's weights).

I.e., the estimated credit tells the block to adjust its weights so that the future outputs move in a direction that appears to reduce the downstream objective.

Now, what is this downstream objective? The objective was measured after the perturbed activation had passed through all remaining blocks and we test three objectives:

Your classic ordinary loss (i.e., average next-token cross-entropy across every token in the batch). I.e., we see if the perturbation improves the model's predictions overall.

Worst token loss (i.e., average loss on approximately the worst-predicted 12.5% of tokens). I.e., does the perturbation improve the individual tokens the model currently finds the hardest?

Window loss (i.e., we find the continuous 16 token window with the highest average loss and measure the error within this window). I.e., did the perturbation improve the model's ability to learn and predict difficult continuous sections of text?

But, improving a temporary activation on the current batch doesn't guarantee that direction into a weight update would necessarily improve the model's ability to learn across future batches (i.e., a direction can produce a nice and immediate descent but still be wonky in the future as weight changes affect many other examples and change future representations).

Since testing many directions requires many extra forward passes (and I am a bit GPU broke at the moment. So, if you have extra GPUs, I would very happily take them) and well, we want to be efficient here, we trained a small neural network to imitate the expensive measurements.

Thus, on occasional query batches, we would: 1) test several activation directions, 2) measure their effects on the downstream loss, 3) combine them into an estimated activation-credit vector, and 4) use that vector as a training label for the predictor.

Between these query batches, the predictor would receive the current unperturbed block activation, info about the final prediction error, and the block's identity in the probe space.

The predictor would then predict the direction that the expensive measurement might have returned (i.e., the goal here is to pay occasionally for an expensive answer and approximate similar answers cost efficiently afterward).

How did we get structured probe directions?

Well, each token's activation had hundreds of dimensions (a few random directions were unlikely to find the useful parts of such a large space). Thus, we created a 32 direction probe basis (i.e., a smaller space to search). Half of the directions came from patterns along which the recent activations varied the most and the other half came from output errors on tokens that were not so nicely predicted.

The intuition here was to pretty much search where the network naturally moves and where its prediction errors suggest something is wrong (i.e., these structured directions worked much more nicely than the random probes).

Exact-gradient controls

We also establish exact-gradient controls to help us figure out two possible limitations:

  1. Perhaps the activation-level global credit is not useful.
  2. The useful activation directions may exist, but perhaps the forward estimator can't recover them accurately (the forward estimator is the perturbation procedure itself where we perturb activation in \(+u\) and \(-u\), measure loss+ and loss−, estimate the slope, and combine slopes into an approx gradient).

For this, we temporarily restored backpropagation through the later blocks and then calculated the exact derivative of the global loss with respect to the earlier activation (the exact gradient here is just a control).

We observed that exact activation credit often worked much better than the forward estimate (i.e., this showed that the useful directions existed, but these sparse forward measurements only recovered the noisy aligned approximations). We experimented with a few structured probes and predictors which eventually produced small gains, but with 16 seeds, we saw the ordinary loss only improving by 0.0015.

When we compare the ordinary local training (with the same total compute since CLC spends more on the probes and predictions) to the counterfactual local credit method (CLC) we observe that the extra local training won by 0.39-0.55 on the factors such as ordinary next-token loss, worst-token loss, and the window loss (i.e., this activation CLC contained a real signal that we could ideally use, but it was too expensive and we want to be efficient).

From gradient estimation to data selection

So, after a long walk with my dog Buster, I came back and thought about this more deeply. The activation CLC approach was trying to estimate hundreds of values, but the data selection approach here would only need to decide which of the four candidate batches a model should train on. So, why don't we try that?

What if we could figure out which of the four candidate batches the model should train on? I.e., a scalar counterfactual here is not nicely suited to reconstruct a large gradient (although it could be well suited to rank 4 choices).

We first experiment with measured one-step improvement. Here, our first data selectors tried to measure how much training on each candidate improved performance on a fixed probe approach. The differences between candidates here were around 0.001 loss units and ordinary variation from one training update to another was much larger.

Hm, so these learned selectors beat uniform sampling and showed that choosing your data carefully could help (albeit they lost to a much simpler idea of selecting the batch where the learner currently has the highest loss). This baseline we mention is called hard-example mining (i.e., find the hard examples).

It didn't seem intuitive to add more features since this wouldn't solve the underlying problem because the measured training labels were noisy (also, we want data-efficiency).

Reducible loss

So, we replaced the noisy one step measurements (i.e., previously, we measure validation/probe loss by training once on a candidate batch A, measure validation or probe loss again, and call the difference A's usefulness, but this was noisy since random variation from a single update was larger; so perhaps the selector was learning from unreliable labels) with a score that could be calculated more directly. We introduce a reducible loss:

Since a high loss example is not always useful (i.e., it may be difficult because 1. the learner has not mastered some learnable pattern or 2. the text is noisy, ambiguous, or just difficult). Thus, we establish a reducible loss. The main learner (i.e., transformer) loss now becomes

\[ \text{learner loss} \approx \text{reducible difficulty} + \text{irreducible difficulty} \]

I.e., the learner is the main model and the reducible loss is the score used to select the data for that model.

We train a small 4-layer, width 192 reference model once on a separate portion of BabyLM data. The reference model here has not seen the learner's training pool, but it has learned related language structure from different documents (i.e., grammar, vocabulary, word relationships, common usage patterns for words, etc.).

For each of the candidate batches, we calculate:

\[ \text{reducible loss} = \text{learner loss} - \text{reference-model loss} \]

The learner loss here is essentially telling us how hard is this batch for the main model now, the reference loss is how hard it is for a separate model trained on related language, and the difference estimates how much of the learner's current difficulty can still be learnable (i.e., we try to quantify this element of how much more we can learn or extract in terms of intelligence, which is still a very open question and philosophical one too).

For an example, we can consider two batches:

BatchLearner lossReference lossReducible loss
A5.02.03.0
B5.04.90.1

Here, the approach of hard-example would see a tie between batch A and batch B because both the learner losses are 5.0. The reducible loss would prefer Batch A because the learner struggles with it (but the reference model handles it pretty well, revealing that there is some learnable structure that can eventually be attained).

Both of the models here also struggle with Batch B, so some of its difficulty in learning may just be noise or ambiguity. The goal of implementing the reference loss here is to have a practical estimate of irreducible difficulty.

We observe that with the reducible loss selection, we outperformed the hard example mining and uniform sampling approach on 8 seeds:

ComparisonMean ordinary-loss difference
Reducible loss − hard-example mining−0.01352
Reducible loss − uniform−0.04567

The reducible loss and standard uniform arms each had a 4,000 update budget and the reducible loss selection reached the uniform arm's final quality after (on average), 0.686x of its own budget! I.e., approx. 31.4% of trained token saving! :D

The selection approach here examines four candidates per update with both the learner and reference model (when uniform training received the same total compute as additional updates, it could train for 10,210 steps). The compute equivalent uniform arm here finished with a 0.00446 lower loss.

Thus, we observed that selection learned more per update token, but at that horizon, its scoring cost was still higher than the benefit…sooooooo…how do we make this more efficient, you ask?

Training longer

I was curious about the results when we trained longer. The reducible loss approach would now perform 6,000 updates and the compute equivalent uniform experiment would allow 15,315 updates. The uniform run would process approximately 2.75 times as many tokens as the experiment's training pool offered (i.e., the first 85% of train.bin).

At the longer horizon, the reducible loss selection did nicer compared to the compute equivalent uniform approach on 8 seeds:

We also ran a repeated comparison using standard end-to-end backprop. At about 2.75 pool passes, the compute equivalent uniform run won by 0.09181 in loss. The stronger end-to-end learner was still doing pretty well in extracting substantial value from another random pass (but it had not saturated as quickly as detached local training). What about if we restrict the learner's pool to the first 25% of train.bin (from 85%)?

Now, the same training work has become approx. 9.4 passes over the small pool. The idea of random reading here didn't work all that nicely, the selection approach got us an ordinary loss that was 0.35085 lower than the uniform approach (i.e., selection did noice on all 8 seeds).

Saturation

So, we began to study the idea of saturation here (since this showed that perhaps the important boundary was not the idea of local training vs backpropagation, but rather data saturation). A natural question here is how many times has the learner already revisited its available data?

This saturation idea goes back to the observation that early in training, almost every random batch contains some useful info and after repeated passes, these common and easy patterns become more and more learned (i.e., we extract the intelligence that we need in terms of patterns, etc.) and it is important to choose the remaining useful examples (this is more valuable).

To figure out how to optimize for selection, we ran several training runs with various pool sizes, horizons, training rules, and seeds; we observe that the REEEE(sults) align with passes over the pool:

Passes over the poolOutcome
1.35The uniform approach wins
≈2–4.6The comparison converged towards the counterfactual selection method
9–18The selection approach won significantly

So, the observation here is that training randomly while another random pass still teaches the model can be helpful, but when these gains from rereading aren't that helpful, we can spend more computation choosing what will give us the best value (and our selection method can be one way of doing that).

Is the reference actually helping?

We also ran an experiment where we compared the real reference with a permuted reference to figure out if this reference info is helpful or not. The real reference here is where each candidate received its correct reference loss and the permuted one is where the same four reference losses were shuffled across the options.

On 8 seeds, we see that the real reference arm does noice!

MetricValue
Mean ordinary-loss difference−0.03558
One-sided exact sign-test p0.00390625

Here, the worst token and worst window loss also favored the real reference on all 8 seeds. From this, we observe two main ideas:

  1. Examining several candidates and choosing a relatively hard one produced most of the large improvement compared to uniform training
  2. Learning to correctly identify which difficulty appeared reducible produced a smaller but reproducible additional improvement.

The takeaway

So, we conclude that in this controlled experiment that reference-informed reducible-loss selection can extract more learning/intelligence from repeatedly seen data compared to uniform rereading once the available pool becomes too saturated. Having the correct reference information here also adds a smaller improvement that does better than the hard example selection approach. The point is backprop is already pretty good at deciding how millions of these model weights should move; the counterfactual information here can become useful when we task it with understanding which experience is still worth learning from (i.e., perhaps not driving straight on a red light)!
